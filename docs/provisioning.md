# 設定與佈建（WiFiManager）

> **注意（2026-10-28）**：本文以原版韌體的設定入口（冷開機後按 **BOOT 鍵**）說明。目前發佈的 HA 版改為
> **冷開機後 LED 亮著的 10 秒內連按兩次 RESET**（原因：有一片板子的 BOOT 腳與 3V3 短路，按 BOOT 等於短路），
> 不需要 OneButton。其餘設計（絕不自動開 portal、逾時、IP 策略）相同。續航數字以早期的 18650 計算，21700 見 [power-budget.md](./power-budget.md)。

使用 WiFiManager 的 captive portal 讓使用者不需重編譯就能設定節點。
但**低功耗專案用 WiFiManager 有兩個會咬人的地方**，先講這兩個，再講設定流程。

## 陷阱一：設定入口網站絕不能自動開啟

WiFiManager 的預設行為 `autoConnect()` 是「連不上就開設定入口網站等使用者來設定」。
**對電池供電的節點，這是災難級的預設值。**

設定入口網站開著時 WiFi AP 全開，約 80 mA。開 3 分鐘就是 **4.0 mAh**：

| 上傳間隔 | 每日總耗電 | 誤開一次 portal 等於 | 若每次喚醒都誤開 |
|---|---|---|---|
| 5 分鐘 | 7.96 mAh | 0.5 天的電 | 電池 **2.1 天**見底 |
| 15 分鐘 | 3.91 mAh | **1.0 天的電** | 電池 **6.2 天**見底 |
| 30 分鐘 | 2.90 mAh | 1.4 天的電 | 電池 **12.3 天**見底 |

路由器重開機、AP 換頻道、鄰居的 WiFi 干擾 —— 任何一個都會讓節點連不上。
如果那時它自動開了設定入口網站，一顆規劃跑一年的電池會在**一週內**耗盡，
而且使用者完全不會知道發生了什麼。

### 對策

```
連線失敗 → 絕不開 portal → 資料存進 pending → 指數退避 → 回去深睡
```

設定模式**只能由人明確觸發**：

| 觸發方式 | 說明 |
|---|---|
| **BOOT 鍵**（採用） | 冷開機後 LED 亮 10 秒，期間按一下 XIAO 板載 BOOT 鍵（GPIO9，用 OneButton 偵測）。載板不必多一顆按鍵 |
| MQTT 指令 | `{"portal": true}`，節點收到指令後立刻開設定頁（約一天才收一次指令） |
| ~~雙擊 reset~~ | 原建議方案，改用 BOOT 鍵：操作更直覺，不用抓兩次 reset 的節奏 |

⚠ 要等 LED 亮了再按：按住 BOOT 再上電 / RESET 會進燒錄模式（GPIO9 是 strapping pin）。

### 開機等待的延遲問題（已有解法）

以下以原本的雙擊 reset 說明；BOOT 鍵等待（10 秒）是同一個問題、同一個解法。

DoubleResetDetector 的原理是「開機後等 N 秒，看有沒有第二次 reset」。
**若每次喚醒都等 3 秒，等於每次視窗多 3 秒 —— 這比整個 WiFi 優化省下的還多，完全不能接受。**

解法是先看喚醒原因，只有人為 reset 才需要判斷：

```cpp
esp_sleep_wakeup_cause_t cause = esp_sleep_get_wakeup_cause();
if (cause == ESP_SLEEP_WAKEUP_TIMER) {
    // 深睡計時器喚醒 = 例行上傳，不可能是使用者按 reset
    // 完全跳過 DRD，零延遲
} else {
    // 上電 / 按 reset / brownout → 才做雙擊判斷（等 3 秒）
}
```

例行喚醒佔了 99.99% 的次數，這條路徑完全不付這 3 秒；
使用者按 reset 時才等，而那本來就是人在旁邊操作的情境。

**注意 brownout 重啟也會走到 else 分支。** 低電量時反覆 brownout 會反覆等 3 秒，
所以 else 分支裡要先檢查電池電壓，過低就直接深睡不做 DRD。

進入設定模式後仍要有三道保險：

1. **硬性逾時**：`setConfigPortalTimeout(180)`，逾時直接深睡，不要無限等待
2. **低電量拒絕**：電壓 < 3.5V 時不開 portal。沒電的時候更不能浪費 4 mAh
3. **設定完成立刻離開**：存檔後馬上關閉 AP 並深睡，不要停留

## 陷阱二：「記住 DHCP 給的 IP 拿來當固定 IP」這個假設不成立

這是你提的做法，方向對，但**前提假設有問題**，而且失敗模式很惡劣。

### 為什麼不成立

1. **DHCP 租約會過期。** 節點改用靜態 IP 之後就不再跟路由器續約，
   租約到期（家用路由器通常 24 小時到 7 天）後那個 IP 就回到可分配池
2. **多數家用路由器有「黏性」**，會盡量把同一個 IP 發給同一個 MAC ——
   所以**短期內通常真的沒事**，這也是為什麼這個做法看起來可行
3. **但 IP 池吃緊時就會被分掉**。訪客手機、新買的 IoT 裝置、
   小孩的平板一多，過期的 IP 就會被拿去用
4. **最關鍵：路由器的衝突偵測對本專案無效。**
   有些 DHCP 伺服器在發 IP 前會先 ping 或 ARP 探測「這個位址有人在用嗎」。
   但我們的節點 **99.9% 的時間在深度睡眠，不會回應任何探測** ——
   路由器會判定那個 IP 沒人用，然後安心地發給別人。
   **一般能保護靜態 IP 的安全網，剛好對深睡裝置失效。**

失敗模式：**佈署後數週才發生，症狀是偶發性連不上或資料斷斷續續，極難追查。**
這是最糟的一種 bug。

### 這個功能值多少：比想像中大很多

先講為什麼值得為它花力氣。靜態 IP 這**單獨一項**的效益（18650）：

| 間隔 | 每次都 DHCP | 記住 IP | 提升 |
|---|---|---|---|
| 5 分鐘 | 5.5 個月 ❌ | **9.9 個月** ✅ | **+80%** |
| 15 分鐘 | 13.0 個月 | **20.1 個月** | +55% |
| 30 分鐘 | 19.9 個月 | **27.1 個月** | +37% |

**5 分鐘模式下，這一項就是達標與不達標的分界線**（5.5 → 9.9 個月）。
所以預設要勾選，而且值得為它做完整的續約與退路機制。

### 對策：三段式 IP 策略 + 自我修復

不需要放棄這個做法，只要加上續約與退路：

| 模式 | 做法 | 適合 |
|---|---|---|
| **自動**（預設） | 首次 DHCP → 記住 IP/GW/mask/DNS → 之後用靜態 | 新手，不必動路由器 |
| **手動** | 使用者自行填入路由器保留的 IP | 會設路由器的人，**最安全** |
| **關閉** | 每次都走 DHCP | 最保險，代價每次多約 1 秒 |

「自動」模式再加兩個機制，把風險壓到可接受：

**1. 每天一次改用 DHCP 續約**

```
if (bootCount % (1440 / interval_min) == 0) 走 DHCP，否則走靜態
```

租約永遠不過期，IP 就不會回到池子。若期間真的被別人占走，
DHCP 伺服器會回 NAK 並給一個新 IP，節點自動重新記錄 —— **自我修復**。

成本：每天多一次 DHCP（約 1000 ms @ 80 mA = 0.022 mAh）。

| 間隔 | 不續約 | 每日續約 | 差距 |
|---|---|---|---|
| 5 分鐘 | 9.9 個月 | 9.9 個月 | 0.28% |
| 15 分鐘 | 20.1 個月 | 20.0 個月 | 0.56% |
| 30 分鐘 | 27.1 個月 | 26.9 個月 | 0.75% |

**代價不到 1%，換掉一個會在數週後爆發的隱性故障 —— 這個交易很划算。**

**2. 失敗就退回 DHCP**

```
靜態 IP 連線失敗 或 連上但 MQTT 失敗
  → 下次喚醒改用 DHCP，重新記錄 IP
  → 標記 flags: ["ip_recache"]
```

`ip_recache` 旗標會出現在 MQTT payload 裡，
**如果某個節點頻繁出現這個旗標，就代表該換成手動指定 IP 或做路由器保留。**

### 設定頁面怎麼呈現

你提到「要新手知道怎麼調整路由器有難度」—— 同意，所以預設就要能動。
建議的措辭（避免出現「DHCP」「子網路遮罩」這種字眼）：

```
☑ 記住 IP 位址以加快連線（推薦）
   第一次連線後會記住路由器分配的位址，之後直接使用，
   每次可省下約 1 秒，電池壽命延長 40~80%。
   若之後連線出問題會自動重新取得，不需要手動處理。

   ▸ 進階設定
     ○ 自動（推薦）
     ○ 手動指定：[192.168.1.50]
       ↳ 請先在路由器將此位址設為保留，這是最穩定的做法
     ○ 關閉（每次重新取得，最保險但較耗電）
```

預設勾選「自動」。**新手完全不用碰路由器，進階使用者有更穩的路可走。**

## 設定項目

| 項目 | 型別 | 預設 | 儲存位置 |
|---|---|---|---|
| WiFi SSID / 密碼 | WiFiManager 內建 | — | NVS |
| **上傳間隔** | 下拉選單 1 / 5 / 15 / 30 分鐘（1 = 續航測試用） | **15** | NVS |
| MQTT broker IP | 文字 | — | NVS |
| MQTT port | 數字 | 1883 | NVS |
| MQTT 帳號 / 密碼 | 文字 | — | NVS |
| 節點名稱 | 文字 | 空（用 MAC 後 6 碼） | NVS |
| 記住 IP | 核取方塊 | **勾選** | NVS |
| 手動 IP | 文字（進階） | 空 | NVS |

上傳間隔的下拉選單用 `WiFiManagerParameter` 的自訂 HTML：

```cpp
const char* interval_html =
  "<label for='iv'>上傳間隔</label>"
  "<select name='iv' id='iv'>"
  "  <option value='5'>5 分鐘（電池約 10 個月）</option>"
  "  <option value='15' selected>15 分鐘（電池約 20 個月，推薦）</option>"
  "  <option value='30'>30 分鐘（電池約 28 個月）</option>"
  "</select>";
WiFiManagerParameter p_interval(interval_html);
```

**把續航數字直接寫在選項裡**，使用者才知道自己在權衡什麼。
（這些數字來自 [`power-budget.md`](./power-budget.md)，改參數後記得同步。）

## 儲存位置：NVS 還是 RTC memory

兩者用途不同，分清楚很重要：

| 資料 | 位置 | 理由 |
|---|---|---|
| WiFi 憑證、間隔、broker 設定 | **NVS** | 幾乎不變，且斷電（換電池）不能遺失 |
| 快取的 IP / 閘道 / 遮罩 | **NVS** | 很少變（只在重新取得時寫入），換電池後仍有效 |
| BSSID + channel 快取 | **RTC memory** | 每次都可能更新，寫 NVS 會磨損 flash；掉了也無所謂 |
| seq、pending 資料、failCount | **RTC memory** | 每次喚醒都變 |

**原則：每次喚醒都可能改的東西不准寫 NVS。**
flash 寫入既耗電（毫秒級、數十 mA）又有壽命限制，
一天寫 288 次、跑兩年就是 20 萬次寫入，會把 NVS 磨壞。

RTC memory 內容在異常重開（brownout、watchdog）後可能是垃圾，**必須做 CRC 校驗**，
校驗失敗就整個歸零，走一次完整的 DHCP + 全頻掃描重建。

## 首次佈建流程

```
1. 燒錄韌體 → 開機發現 NVS 沒有設定 → 自動進入設定模式
2. 手機連上 AP「EnviroSense-a1b2c3」→ 自動跳出設定頁
3. 選 WiFi、輸入密碼、選上傳間隔、填 broker IP
4. 存檔 → 節點以 DHCP 連線
5. 連線成功 → 記錄 IP / 閘道 / 遮罩 / DNS / BSSID / channel
6. 發一次 Home Assistant 自動探索（retain）
7. 送出第一筆資料 → 深度睡眠
```

**只有第 1 步的「NVS 沒有設定」會自動進入設定模式。**
之後任何連線失敗都不會再自動開 portal，只能靠 BOOT 鍵手動觸發。

## WiFiManager 的體積代價

WiFiManager 會拉進 WebServer + DNSServer，binary 明顯變大。
影響喚醒時間的地方在於：**若沒開 `CONFIG_BOOTLOADER_SKIP_VALIDATE_IN_DEEP_SLEEP`，
bootloader 每次醒來都要對整個映像算 SHA256，時間與映像大小成正比。**

也就是說 —— **加入 WiFiManager 會讓「跳過映像驗證」這項優化從可有可無變成值得做**，
但那項在 Arduino framework 下改不了（見 [`wifi-optimization.md`](./wifi-optimization.md)）。

M2 必須實測：加入 WiFiManager 前後的喚醒視窗差多少。
若差距顯著，備案是把設定入口網站切到獨立的 app partition，
平時執行的精簡韌體不含 WebServer —— 但那會讓專案複雜不少，非必要不做。
